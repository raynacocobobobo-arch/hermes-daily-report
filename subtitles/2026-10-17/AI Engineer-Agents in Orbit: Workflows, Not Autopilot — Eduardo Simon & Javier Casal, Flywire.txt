>> This bring us to Orbit, our own toil

Instead of letting AI agents run freely

So what does a workflow actually look
like? Every agent in orbit is defined in
a single JML file that lives in a
repository and goes through the same
merge request review as any other code.
Take our code review agent as an
example. It starts with a trigger, a
Gilda web hook that fires when an
engineer mentions the review bot on a
merge request. From there, a sequence of
deterministic activities, fetches the
merge request metadata, classifies its
risk tier, loads prior findings and
clones the repository only. Then we call
the model in an LLM step that can read
the code but has no permission to modify
it and that must answer in a strict
output schema. Finally, another
deterministic step post the findings
back to the mer request. This is what we
mean by workflows, not autopilot. Code
handles the predictable parts and the
model is called only where reasoning is
actually needed.
We choose to start with JAML files and a
request review process on purpose. YAML
is a format our engineers already know
and the review works the way they
already work every day. It also keeps
the codebase AI friendly. Coding agents
can read, write, and review workflow
definitions as easily as people can.

Let's take a deeper look at the
technical architecture of Orbit.
Originally we began with a simple
container setup on AWS ECS Fargate where
the orchestration layer harness and the
runtime environment lived inside the
same container. As our needs grew, we
evolved towards separating the
orchestration layer, the agent runtime
environment and the session state into
distinct components. This improves
isolation, maintainability and resource
allocation. It also makes the system
more resilient because an error in the
effort does not kill the sandbox and it
lets us scale each piece independently
and adapt to changing requirements.
Fargate lets us scale task elastically
so we can run a very large number of
agents in parallel. It was also really
easy to deploy orbit because we already
had Victoria our past that scales
applications without any effort. But
that scale needs guard rails. so the
platform is not misused. First,
timeouts. Every agent stops after a
configurable amount of time. Second, red
limits, which are aggressive by default.
A broken API integration could start
spawning thousands of agents and make
our build much bigger. The limits keep
that under control. Third, concurrency
control. Our control plane uses locks to
prevent duplicate executions of the same
task. For example, if a code review is
already running, we drop the duplicated
request.
Running agents in a Victoria comes with
container limits. Victoria uses standard
Fargate task definitions. So the
containers are lightweight and tightly
restricted. Our baseline agent container
includes the common language runtimes.
But it intentionally leaves out package
managers like Bundler, Maven, and
Composer. So heavy agents like our Jer
implement cannot easily run native
builds or unit tests inside the
container.
When we started orbit in April, AWS
Lambda microVMs did not exist yet. AWS
released them in June. So our first
version run only on Fargate.
These are managed microVMs that work
like Lambda functions resumable
processes. So they can pause and
continue where they stop. that fits the
nature of agentic execution really well.
So we now use them with a runtime chosen
by project type. Each tech stack gets
its own tool chain quickly in an
isolated environment. This is not full
sandboxing yet and we are actively
moving there. The goal is to support
setups like dockering docker or multiple
microvms so agents can run test or more
complex verifications on any repository.
Inside each LLM step, we did not build
our own harness. Instead, we reuse the
clot agents SDK, the same harness that
powers cloud code. This gives us a
mature, well- tested harness with tool
usage, sub aents, and skills out of the
box. So, we can focus on the workflow
rather than on the plumbing. What we add
on top is control. We restrict four
different things for every step. the
network the agent can reach, the tools
it can call, the skills it can load, and
the MCP servers it can use down to the
specific tools allowed from each server.
All of this is declared in the YAML file
itself. A code review step, for example,
can read and search the code, but cannot
edit files or push changes. And our
central investigator can query traces
through our MCP server, but only with a
short list of readonly tools. In
practice, each LM step runs with only
the axis it needs and the axis is
visible and reviewable like any other
code.
Skills themselves come from a single
place. At Flywire, we maintain a central

Once a team is sure that a task is worth
automating, we move it into orbit and
turn it into a workflow. The predictable
parts become deterministic code. The
model is called only where it adds
value, and each run becomes more
reliable and less expensive than an
open-ended session. Workflows also run
in the background, so engineers do not
have to sit with an open session and
guided step by step. That means less
context switching and more time for the
work that needs them.
Beyond runtime isolation, we also rely
heavily on structure output to guarantee
systemic reliability.
every LM step in an orbit workflow
enforces strict JSON schemas for model
responses. By constraining output
formats, we ensure that subsequent
execution branches, error handling, and
state transitions are driven by
terministic control flow rather than
unpredictable string parsing. If an NLM
response fails validation against the
expected JSON schema, Orbit
automatically triggers a targeted retry
or fallback pass before proceeding.
Another crucial pattern we rely on is
isolated component evaluation.
Evaluating complex end to end agentic
workflows in synthetic benchmark
environments is often noisy, expensive,
and difficult to reproduce consistently.
Instead of trying to evaluate entire
workflows from start to finish, our
evaluation harness isolates individual
LLM steps. By injecting exact historical
state and context directly into specific
workflow nodes, we can evaluate model
output quality, measure PROM
adjustments, and catch performance
regressions quickly and cost
effectively. So, how do we know that an
agent is good enough? Today, a new agent
usually reaches production after a b
check. The team tries it on a few real
cases and confirms that it behaves as
expected. Once it runs in production, we
trace every execution end to end with
open telemetry, including each activity,
model call, and tool call. We then
extract traces from real executions and
add them to a golden data set. For now,
each golden data set is version in the
repository next to the code and we run
it on demand. Based on those results, we
improve the prompt or change the model
and we run the data set again to
compare. We do not have online
evaluations yet, but we are working on
them internally. Our goal is to run the
whole evaluation loop inside orbit from
the UI or through the MCP server. First,
you deploy your agent. Then, you monitor
and evaluate its execution in
production. Finally, you improve the
agent based on those evaluations without
the need to deploy it again.
That is our Roma for evaluations. One
place to ship, measure and improve every
workflow.
